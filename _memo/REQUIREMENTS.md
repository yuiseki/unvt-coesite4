# coesite4 近代化プロジェクト要件定義書

## 1. 概要

本ドキュメントは、ベクトルタイルサーバー `coesite4` を、2025年時点の最新ソフトウェアエンジニアリングのベストプラクティスに基づき、堅牢性、スケーラビリティ、保守性を備えたモダンなアプリケーションとして再構築するための要件を定義する。

## 2. 機能要件

既存のコア機能は維持、または強化する。

- **ベクトルタイル配信**: MBTiles ファイルをデータソースとし、指定された `z/x/y` に基づいてベクトルタイルを配信する。
- **認証**: Microsoft Identity Platform (Azure AD) を用いたユーザー認証機能を提供する。
- **設定ベースのデータソース**: 設定ファイルに基づき、配信するタイルソースを動的に管理できる。
- **API**: クライアントアプリケーションが必要とするデータを提供するセキュアなAPIエンドポイントを持つ。

## 3. 非機能要件

### 3.1. 技術スタック

- **言語**: **TypeScript** を全面的に採用する。静的型付けによるコンパイル時のエラー検出、コード補完の強化、リファクタリングの安全性向上を図る。
- **ランタイム**: **Node.js** の最新LTSバージョンを使用する。
- **フレームワーク**: **Express.js** を継続利用するが、TypeScriptとの親和性を高めるためのラッパーやデコレーターを導入するか、よりモダンなフレームワーク（例: **NestJS**）への移行を検討する。
- **データベースアクセス**: **Prisma** や **TypeORM** のようなモダンなORMを導入し、型安全なデータベース操作を実現する。SQLインジェクションのリスクを低減し、マイグレーション管理を容易にする。

### 3.2. アーキテクチャ

- **レイヤードアーキテクチャ**: 関心の分離を徹底するため、以下のレイヤーで構成する。
    - **Controller (API) Layer**: HTTPリクエストの受付とレスポンスの返却に責務を限定する。
    - **Service (Business Logic) Layer**: アプリケーションのコアなビジネスロジックを実装する。フレームワークに依存しない純粋なTypeScript/JavaScriptで記述する。
    - **Repository (Data Access) Layer**: データベース、MBTilesファイル、外部APIなど、データソースへのアクセスを抽象化する。
- **Dependency Injection (DI)**: DIコンテナ（例: `tsyringe`, `InversifyJS`）を導入し、クラス間の依存関係を外部から注入する。これにより、コンポーネントの疎結合化とテストの容易性を実現する。

### 3.3. コード品質と開発者体験

- **静的解析**: **ESLint** と **Prettier** の導入を必須とし、コーディング規約を強制する。コミット時に自動でフォーマットが実行される仕組み（Husky + lint-staged）を導入する。
- **非同期処理**: プロジェクト内のすべての非同期処理は **`async/await`** を用いて記述する。旧来のコールバックやPromiseチェーンのネストは排除する。
- **テスト**:
    - **ユニットテスト**: Service層や純粋な関数など、ビジネスロジックの最小単位をテストする。
    - **インテグレーションテスト**: 複数のコンポーネント（Controller, Service, Repository）を連携させ、APIエンドポイントレベルでの動作を検証する。
    - **カバレッジ**: テストカバレッジの目標値を設定し（例: 80%以上）、CIで常に監視する。
- **ビルドプロセス**: `tsc` によるコンパイルに加え、`esbuild` や `swc` を利用した高速なトランスパイル環境を開発用に導入する。

### 3.4. 設定管理

- **環境変数**: データベース接続情報、APIキー、セッションシークレットなど、環境に依存するすべての設定は環境変数から読み込む。
- **設定の検証**: アプリケーション起動時に、必要な環境変数がすべて設定されているかを **Zod** などのライブラリを用いて検証し、不足している場合はエラーを出して起動を中止する。

### 3.5. API設計

- **スキーマ駆動開発**: **OpenAPI (Swagger)** 仕様を用いてAPIを定義し、ドキュメントを自動生成する。
- **リクエスト検証**: APIへのすべての入力（body, params, query）は、Zodなどを用いて厳密にバリデーションする。

### 3.6. セキュリティ

- **依存関係**: `npm audit` や `Snyk` などのツールをCIに組み込み、依存パッケージの脆弱性を継続的に監視する。
- **コンテナセキュリティ**: 本番用のDockerイメージは、脆弱性の少ない軽量なベースイメージ（例: `node:lts-alpine`）を使用し、rootユーザーでの実行を避ける。

### 3.7. 運用・保守性

- **ロギング**: **Winston** や **Pino** を使用し、すべてのログを構造化されたJSON形式で出力する。ログレベル（info, warn, error）を適切に使い分ける。
- **ヘルスチェック**: コンテナオーケストレーター（Kubernetesなど）からの死活監視のため、`/healthz` のようなヘルスチェック用エンドポイントを実装する。
- **コンテナ化**:
    - **Dockerfile**: 開発用と本番用で最適化されたDockerfileを作成する。本番用はマルチステージビルドを活用し、`devDependencies` を含めない軽量なイメージを生成する。
    - **Docker Compose**: データベースを含めた開発環境全体を `docker-compose.yml` で定義し、ワンコマンドでローカル開発環境を構築できるようにする。

## 4. 成果物

- TypeScriptで再構築されたアプリケーションのソースコード。
- 上記非機能要件を満たすための各種設定ファイル（`.eslintrc.js`, `tsconfig.json` など）。
- ユニットテストおよびインテグレーションテストのコード。
- 本番デプロイ用の `Dockerfile`。
- ローカル開発環境用の `docker-compose.yml`。
- 自動生成されたOpenAPIドキュメント。
- プロジェクトのセットアップ、設定、デプロイ方法を記述した `README.md`。
